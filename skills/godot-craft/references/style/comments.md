# GDScript Commenting and Documentation Guidelines

This document defines the rules and best practices for code commenting and API documentation in GDScript for Godot 4.x projects. Standardizing these comments ensures high-quality editor tooltips, autogenerated documentation, and clear distinction between public contracts and internal implementation logic.

## 1. Double-Hash for Documentation and API Comments

Use double-hash `##` comments placed directly above class definitions, constants, and member declarations for API-level documentation. For constants, describe their purpose, unit of measurement, and any constraints.
- **Reason:** Prefixing comments with `##` enables Godot's built-in documentation generator to parse them, generating editor tooltips and documentation pages. Removing blank lines between the comment and the declaration binds the documentation to the correct member.

```gdscript
# Good
## A controller representing a player character in 2D space.
##
## Manages physical movement, inputs, and animations.
class_name PlayerController
extends CharacterBody2D

## The maximum speed threshold for the physical engine.
## Unit: Pixels per second (px/s).
## Constraint: Must be a positive value greater than zero.
const MAX_SPEED: float = 400.0

## The maximum walk speed of the player.
@export var speed: float = 300.0


## Calculates the final velocity modifier based on terrain.
func calculate_velocity_modifier() -> float:
	return 1.0
```

```gdscript
# Bad
# A controller representing a player character in 2D space.
class_name PlayerController
extends CharacterBody2D

## The maximum walk speed of the player.

@export var speed: float = 300.0


# Calculates the final velocity modifier based on terrain.
func calculate_velocity_modifier() -> float:
	return 1.0
```

## 2. Single-Hash for Inline Comments Explaining "Why"

Use single-hash `#` comments within function blocks to explain the intent, invariants, and decisions behind the code, rather than narrating what the code does.
- **Reason:** Statically-typed, clean code explains *what* is happening. Comments should capture non-obvious context, complex math, or safety constraints (*why*), preventing code noise and reducing maintenance overhead.

```gdscript
# Good
extends CharacterBody2D

var _jump_count: int = 0

var _is_jumping: bool = false


func _physics_process(_delta: float) -> void:
	# Reset jump flags only when touching the ground to allow coyote time
	if is_on_floor():
		_jump_count = 0
		_is_jumping = false
```

```gdscript
# Bad
extends CharacterBody2D

var _jump_count: int = 0

var _is_jumping: bool = false


func _physics_process(_delta: float) -> void:
	# If is_on_floor is true
	if is_on_floor():
		# Set jump_count to 0
		_jump_count = 0
		# Set is_jumping to false
		_is_jumping = false
```

## 3. Documenting Deprecated and Experimental APIs with BBCode Doc-Comment Tags

Document deprecation and experimental status solely via BBCode doc-comment tags (such as `[deprecated]` or `[experimental]`) inside double-hash `##` comments. You must not use decorators or annotations starting with `@` in the code.
- **Reason:** Relying on standard BBCode doc-comment tags keeps the code layout clean, avoids decorator complexity, and ensures complete compatibility with the editor's generated tooltips without introducing extra annotations.

```gdscript
# Good
extends Node


## The original physical calculation for actor velocity.
##
## [deprecated] Use [method calculate_velocity_modifier] instead.
func calculate_speed() -> float:
	return 10.0


## Experimental physics pathing for flying actors.
##
## [experimental] Unstable system under active review.
## May change or be removed in future updates.
func path_to_target_3d(target: Vector3) -> Array[Vector3]:
	var path: Array[Vector3] = []
	path.append(target)
	return path
```

```gdscript
# Bad
extends Node


## The original physical calculation for actor velocity.
# @deprecation_decorator
func calculate_speed() -> float:
	return 10.0


## Experimental physics pathing for flying actors.
# @experimental_decorator
func path_to_target_3d(target: Vector3) -> Array[Vector3]:
	var path: Array[Vector3] = []
	path.append(target)
	return path
```

## 4. Documenting Signals and Exports with Context and Parameters

Use double-hash `##` comments to document signals and exports, specifying emitting triggers, inspector constraints, and function parameters with BBCode-like markup.
- **Reason:** Signals and exports represent the primary boundaries of scene communication and editor configuration. Documenting them enables rich tooltips in the Inspector and correctly generates parameter details in the internal API documentation.

```gdscript
# Good
extends Node

## Emitted when the character takes damage.
## [param current_health] The health remaining after damage is applied.
## [param damage_amount] The raw damage value subtracted.
signal damaged(current_health: int, damage_amount: int)

## The speed modifier applied when the character is sneaking.
## Value must be between 0.0 (stopped) and 1.0 (full speed).
@export_range(0.0, 1.0) var sneak_multiplier: float = 0.5
```

```gdscript
# Bad
extends Node

signal damaged(current_health: int, damage_amount: int)

# The speed modifier for sneaking
@export var sneak_multiplier: float = 0.5
```

## 5. No Commented-Out Dead Code

Avoid leaving commented-out blocks of code in scripts; delete dead code and rely on version control for history.
- **Reason:** Commented-out code causes visual noise, confuses developers about the actual behavior, and rots over time since refactoring tools ignore it.

```gdscript
# Good
extends Node

var speed: float = 300.0

var default_speed: float = 300.0


func _ready() -> void:
	_initialize_player()


func _initialize_player() -> void:
	speed = default_speed
```

```gdscript
# Bad
extends Node

var speed: float = 300.0

var default_speed: float = 300.0


func _ready() -> void:
	# speed = 100.0
	# print("initializing player...")
	_initialize_player()


func _initialize_player() -> void:
	pass
```

## 6. Checklist

- [ ] Class description doc-comments (`##`) are placed at the absolute top of the block, before `class_name` and `extends` declarations.
- [ ] Constants are documented using double-hash `##` comments detailing purpose, unit of measurement, and constraints.
- [ ] Export variables and signals have double-hash `##` comments with no blank lines between comments and declarations.
- [ ] Double-hash comments (`##`) use BBCode-like formatting such as `[param name]` or `[method name]` to link definitions.
- [ ] Inline comments use single-hash `#` and explain "why", not "what".
- [ ] Deprecated and experimental APIs are documented solely via BBCode doc-comment tags (such as [deprecated] or [experimental]) inside double-hash comments, with no use of decorators/annotations starting with @.
- [ ] Stale or commented-out code blocks are completely deleted.
